# Правила работы с Game Encyclopedia

Эти правила действуют для всего репозитория. Перед изменениями прочитай относящийся к задаче раздел [PROJECT_DOCUMENTATION.md](PROJECT_DOCUMENTATION.md), затем текущие исходники. При расхождении документа и кода уточняй фактическое поведение по исходникам и тестам; не восстанавливай старую реализацию автоматически.

## Область изменений

- Сохраняй существующий внешний вид, поведение и игровую логику, если пользователь явно не запросил их изменение.
- Не переписывай приложение и не вводи новые библиотеки, хранилища или системы стилизации без конкретной необходимости.
- Не создавай лишние компоненты и абстракции. Сначала найди и переиспользуй существующие компоненты, функции и хуки.
- Не удаляй пользовательские изменения и не применяй destructive Git-команды.
- Не редактируй `dist` или `node_modules` как исходный код.

## Игровая логика

- Редьюсеры — `src/store`, расчёты — `src/engine` и профильные `src/utils`. UI не должен дублировать формулы.
- Не меняй JSON, ключи данных, числовые значения, единицы измерения и ограничения характеристик без явного задания. Особенно сохраняй `attack_spead` и различие единиц героев/противников.
- Не мутируй базовые данные. Бонусы пересчитываются от исходных значений, лимиты героя применяются после суммирования.
- Арканы: 4×3, только ортогональные соседи; `arcanas_bonus` не усиливается соседями. Случайная цель — слот, включая пустой; выбирается при commit, не в render/preview.
- Уникальные эффекты Арканов 5, 9, 11, 16, 29, 37, 39, 40 и пассивки Некроманта, Демона, Феи и Призрака рассчитываются в общем конвейере `calculateHeroBuild`. Остальные unique-эффекты остаются описаниями. Не переносить формулы в визуальные связи.
- Ручной уровень Аркана — 1–15, итоговый — до 20; бонус уровней округляется вниз. «Влюблённые», «Суд» и «Император» не получают бонусные уровни. «Колесница» получает уровни от других карт и собственные +1. Бонусные уровни не сохраняются вместо ручных. «Умеренность» даёт одной способности +1, максимум 6; Фея и соседское усиление не увеличивают количество добавляемых уровней.
- Предпросмотр, hover и drag не сохраняют сборку до подтверждённого действия. Отмена перетаскивания не снимает карту/предмет.
- Для допустимости назначения Аркана используй `canAssignArcanaAbility`, для отображения чисел — `formatNumber`.
- Сохраняй совместимость localStorage `eternal-battle-build-v1`. Новые поля должны безопасно восстанавливаться из старых сохранений.

## CSS

- Не дублируй CSS. Все стили компонента, состояния и модификаторы располагай в одном логическом месте; не добавляй повторный селектор в конец файла для исправления каскада.
- Перед правкой найди правило и все его responsive/страничные модификаторы. Учитывай специфичность и порядок импортов в App.
- Общие подсказки — `tooltips.css`; игровая сцена/панель — `heroes.css`; остальные стили — профильные файлы. `transitions.css` содержит общую межстраничную координацию.
- Переиспользуй существующие токены. Не объединяй намеренно разные оттенки, размеры и скорости переходов под видом рефакторинга.
- Не удаляй классы по одному статическому поиску: проверь шаблонные строки, portals, aria/data-состояния и вычисляемые имена.
- Сохраняй порядок SVG/рамок/иллюстраций, pointer-events, cqw/svh-ограничения и reduced-motion.
- `!important` допускается только с конкретной причиной; существующие `[hidden]`, общий reduced-motion и mobile overrides inline-координат имеют такую причину.

## Ресурсы и жизненный цикл

- Используй текущие функции построения путей и явные исключения имён. Не удаляй изображения без проверки динамических ссылок и JSON.
- Подписки, таймеры и ResizeObserver должны иметь очистку; асинхронная загрузка не должна применять устаревший результат.
- Не добавляй useMemo/useCallback автоматически: сначала установи повторяющуюся работу или измеримую проблему.

## Проверки и документация

- На Windows запускай `npm.cmd run lint`, `npm.cmd test`, `npm.cmd run build`; при изменении компонентов также `npm.cmd run test:render`.
- Добавляй тесты для новой логики и исправлений поведения; не создавай тесты, лишь повторяющие реализацию простого визуального изменения.
- Не отключай проверки ради зелёного результата. Отделяй ограничения среды от ошибок приложения.
- SSR не заменяет браузер. Если доступен браузер, проверяй затронутые страницы и размеры. Если недоступен — явно сообщи об этом, не заявляй о визуальной идентичности.
- При изменении архитектуры, CSS-владельцев, сохранений, механик или команд обновляй `PROJECT_DOCUMENTATION.md` и относящиеся заметки. Существенные результаты аудита фиксируй в `CODE_REVIEW_REPORT.md`.
- В итоговом сообщении укажи сделанные изменения, проверки и реальные ограничения. Документация проекта — на русском языке.
